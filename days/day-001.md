## Learning Plan — Days 2–10

Before building the larger projects, I want to establish the fundamentals of modern AI systems through small experiments rather than only reading theory.

### Day 2 — LLM Mental Model
Understand what actually happens between sending a prompt and receiving an answer.

### Day 3 — Tokens
Understand what a token is and why tokenisation matters.

Experiment with:
- Normal English

- Numbers
- Asset IDs and registration numbers
- JSON
- Marathi and other languages

Observe how text is broken into tokens and connect token counts to context-window limits, latency and API cost.

### Day 4 — Context
Understand what information an LLM actually has available during a request.

Experiment by providing information in one API call and withholding it from another.

### Day 5 — Instructions & Prompting
Understand system/user messages and how instructions and context affect model behaviour.

### Day 6 — Probabilistic Output
Explore why the same input can produce different outputs and understand parameters such as temperature.

### Day 7 — Structured Outputs
Learn how probabilistic language-model output can be constrained into predictable, machine-usable structures such as JSON.

### Day 8 — Embeddings
Understand how software can find information by meaning rather than exact words.

Experiment using synthetic construction pay items such as "diesel for excavator" and "fuel supplied to plant".

### Day 9 — RAG
Understand how retrieval, embeddings and context can allow an LLM to answer using information outside its training data.

### Day 10 — Tools & Agents
Understand how an LLM moves beyond generating text and can request actions from APIs, databases and functions.

## AI Principle Learned Today

**Use AI for ambiguity; use deterministic code for certainty.**

For example, AI may interpret an invoice and extract the total because the input is unstructured.

Once the total is known, an exact business rule such as:

> Invoices above $1,000 require manager approval.

should normally be enforced by deterministic application code rather than asking an LLM to make the decision.

Over the next nine days, I want to build enough understanding to explain how these pieces fit together:

**Tokens → Context → Instructions → Probabilistic Output → Structured Outputs → Embeddings → Retrieval/RAG → Tools → Agents**
## The problems I want to explore

### 1. Invoice Intelligence
Read an invoice and extract the required information into structured fields.

### 2. Sustainability Classification
Suggest appropriate sustainability tags for vendor pay items.

### 3. Waste Document → Material Docket
Read a waste destination/tip-site document and transform the relevant information into a material docket upload file.

### 4. Intelligent Plant Identification
Allow a user to enter an imperfect plant identifier and determine the correct plant using available information such as:

- Plant name
- Asset ID
- LV number
- PPID
- Registration number

The system should deal with incomplete or slightly incorrect input rather than requiring an exact database match.

### 5. Plant Forever
Explore a system for plantation programs where someone photographs a newly planted tree and records its GPS location.

The photograph, location and associated information become a persistent digital record of that plant that can be referenced and revisited over time.

The idea could potentially be generalised beyond a single NGO or plantation program.

## What I learned

### GitHub

Today I created my first new GitHub project in years and started understanding the basic workflow:

**Repository → Files → Changes → Commit**

A commit creates a recorded version of a change, allowing the history of the project to be followed over time.

### GitHub fundamentals

A repository is the complete project together with its version history.

`main` is the default branch containing the current official version of the project.

A branch creates a separate line of development where changes can be made without immediately changing `main`.

A commit records a set of changes as a point in the project's history.

A pull request proposes bringing changes from one branch into another and provides an opportunity to review them.

A merge incorporates the changes from one branch into another.
