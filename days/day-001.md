## Problems I Want to Explore

### 1. Invoice Intelligence

Read an invoice and extract the required information into structured fields.

### 2. Sustainability Classification

Suggest appropriate sustainability tags for vendor pay items.

### 3. Waste Document → Material Docket

Read a waste destination/tip-site document and transform the relevant information into a material docket upload file.

### 4. Intelligent Plant Identification

Allow a user to enter an imperfect plant identifier and determine the correct plant using available information such as:

- Plant name
- Asset ID
- LV number
- PPID
- Registration number

The system should deal with incomplete or slightly incorrect input rather than requiring an exact database match.

### 5. Plant Forever

Explore a system for plantation programs where someone photographs a newly planted tree and records its GPS location.

The photograph, location and associated information would become a persistent digital record of that plant that could be referenced and revisited over time.

The idea could potentially be generalised beyond a single NGO or plantation program.

## What I Learned

### GitHub Fundamentals

A **repository** is the complete project together with its version history.

`main` is the default branch containing the current official version of the project.

A **branch** creates a separate line of development where changes can be made without immediately changing `main`.

A **commit** records a set of changes as a point in the project's history.

A **pull request** proposes bringing changes from one branch into another and provides an opportunity to review them.

A **merge** incorporates those changes into the target branch.

Today I practised the complete workflow:

**Repository → Branch → Change → Commit → Pull Request → Merge**

## AI Principle Learned Today

### Use AI for ambiguity; use deterministic code for certainty.

For example, AI may interpret an invoice and extract its total because the source document is unstructured.

Once that total has been extracted, an exact business rule such as:

> Invoices above $1,000 require manager approval.

should normally be enforced by deterministic application code rather than asking an LLM to make the decision.

This distinction — deciding which parts of a problem actually need AI — will be important throughout the 100 days.

## Learning Strategy

The objective is not to learn AI as a collection of isolated concepts.

I want to start with real problems and learn the necessary AI concepts while trying to solve them.

Before building the larger projects, Days 2–10 will establish the foundations through small experiments:

| Day | Topic | Question |
|---|---|---|
| 2 | LLM Mental Model | What actually happens between sending a prompt and receiving an answer? |
| 3 | Tokens | What is a token and why does tokenisation matter? |
| 4 | Context | What information does an LLM actually have available during a request? |
| 5 | Instructions & Prompting | How do instructions and context affect model behaviour? |
| 6 | Probabilistic Output | Why can the same input produce different outputs? |
| 7 | Structured Outputs | How do we turn LLM output into predictable machine-usable data? |
| 8 | Embeddings | How can software find information by meaning rather than exact words? |
| 9 | RAG | How can an LLM use information outside its training data? |
| 10 | Tools & Agents | How can an LLM interact with APIs, databases and functions? |

The aim is to eventually understand how these pieces connect:

**Tokens → Context → Instructions → Probabilistic Output → Structured Outputs → Embeddings → Retrieval/RAG → Tools → Agents**
